Iter-9 Integration Map — Where each new workstream plugs in

Below: each W-workstream's exact insertion point in the pipeline above, the tangible value it adds, and the iter-7 finding it would have prevented.

W6-lite — Regression harness

Plug-in pointOut-of-band CI step. Triggered on every commit that touches scripts/serial-design-chain-v2.tsx, src/lib/pdf-engine-v2/radical/*, src/lib/pdf-engine-v2/class-*.ts, or scripts/render-minimal-pdf.tsx. Does NOT change the production chain.
What it doesRuns 15 golden briefs (5 each for VF + BESS + heatpump) through the chain. Compares output state.json against frozen invariants: gate-pass counts ±tolerance, BoM total within class band, manual-review badge counts, performance card warning count, design decisions count by status. Diff fails → CI blocks merge.
Run time~7 hrs (15 briefs × 28 min each, parallelisable to 1-2 hrs with multi-Mac-Studio or cloud GPU)
Tangible value: the K10 cross-class bleed fix today narrowly missed introducing a regression on heatpump (which DOES have `energy_storage_source` as a required module). Without a heatpump regression test, I'd have shipped a fix that protected VF and broke heat pump.

W0 — Canonical Object Model

Plug-in pointNEW file src/lib/pdf-engine-v2/object-model/. Replaces the scattered registries (class-priors.ts, class-connections.ts, class-suppliers.ts, class-standards.ts, class-floors.ts) as VIEWS over a single typed graph. Consumed by:
  • Pre-Phase-1 (G1b compliance) — typed standards per archetype
  • Phase 1 Generator — emits against typed schema, not free prose
  • Phase 2 grammar gates — required connections derived from object graph
  • Engine B — typed BoM (component_class is a property of the object, not Flash-Lite guess)
  • Engine D — suppliers tied to specific object instances
What it addsOne source of truth per class. VerticalFarm.AirHandlingUnit has typed fields { static_pressure_pa, fan_size_mm, fan_type }. Generator can't emit an axial fan at 150 Pa because the type system rejects it. K10 cross-class bleed cannot happen because VerticalFarm doesn't have an EnergyStorageSource sub-class.
Tangible value: iter-7 findings I (K10 bleed) + B (LED 10× driver mismatch) + C (fan stall) + H (duplicate BoM rows) would all be caught at TYPE-CHECK TIME, not at runtime by gates. Would have prevented 4 of 10 iter-7 findings from ever existing.

W1 — Deterministic engineering tools (in-flight)

Plug-in pointTwo integration modes:
  • In-flight (Gemini function-calling): Generator at STEP 4 gains tools=[psychrometrics, fan_curve, voltage_drop, refrigerant_cycle, pressure_drop]. When emitting HVAC module, Generator calls psychrometrics.calc(temp_db=22, rh=70, alt=20) → gets dewpoint, enthalpy → sizes reheat coil accurately.
  • Post-hoc verification: each Phase 2 arithmetic gate that currently has a lookup table calls the tool instead. fanStaticPressureFeasibilityGate calls fan_curve.lookup(size, type) not a hardcoded table.
What it addsDeterministic physics replaces LLM guessing. Tool always returns {value, source, uncertainty} — no fake determinism. Cached by (tool, inputs-hash).
Tangible value: iter-7 findings B (LED driver mismatch) + C (fan stall) + D (RO pump pressure 6× short) directly prevented. Generator wouldn't have emitted a 300mm axial fan at 150 Pa because `fan_curve.lookup(300, 'axial')` returns max 100 Pa and Generator sees that BEFORE writing the spec.

W4 — Adversarial dev (steel-man + red-team)

Plug-in pointNEW pre-merge CI check on chain-critical files. Triggers on PR creation to those paths. Dispatches 2 LLMs steel-manning the BEFORE state + 2 LLMs red-teaming the AFTER state.
What it addsSurfaces regressions that the developer (me) and the council (audit-after-the-fact) miss. Output committed alongside the change.
Tangible value: commit decdcdfa6 introduced a name collision (DesignDecisionsPage clash with Section 4) — type-check caught it after push, fixed in c50bfb933. Red-team would have caught it BEFORE merge.

W3 — Mixture of Domain Experts

Plug-in pointReplace the R1-R4 generic reviewer slots (STEP 5-8) with class-aware specialist routing. Each module gets its domain expert: Module 2 (HVAC) → HVAC expert, Module 5 (Electrical) → Electrical expert, etc.
What it addsSpecialist prompts + tool access. HVAC expert has psychrometrics + refrigerant_cycle tools + ASHRAE prompt. Electrical expert has voltage_drop + BS 7671 prompt. Each fights for its corner.
Tangible value: iter-7 finding B (LED 10× mismatch) survived 4 generic reviewers but would not have survived an Electrical expert who's prompted to check driver-load relationships explicitly.

W7 — In-Context Learning via curated exemplar packs

Plug-in pointPre-Phase-1: a retrieval step BEFORE STEP 4 Generator. Retrieves 2-3 golden reports by (class, envelope, scale) similarity. Injects as in-context examples to Generator AND each W3 specialist.
What it addsClass-specific gold-standard templates. VF 100m² container brief retrieves the BEST VF container example, not a 4-8m² cabinet example. Generator starts from a real working pattern instead of from-scratch.
Tangible value: iter-7 finding A (Engine B under-pricing) — if the exemplar pack included a real 100m² VF with realistic prices, Generator would emit prices in the right magnitude from the start, before Engine B even runs.

W5 — Pattern distillation

Plug-in pointOffline batch job. Consumes the last ≥20 runs per class from chain_telemetry. Proposes registry diffs (class-priors additions, Engine B anchor updates, supplier catalogue updates). Diffs go to a PR queue — human (Tristan) reviews + merges.
What it addsCloses the loop on what we did manually today. Today: I noticed VF had only 4 component overrides; expanded to 12. W5 detects this drift automatically and proposes the update.
Tangible value: the iter-5 → iter-7 generalisation gap (heat pump Engine B fix didn't generalise to VF) would be caught automatically after 20 VF runs showed the same under-pricing pattern.

W2 — Multimodal reference grounding

Plug-in pointNEW chain step between K10 and Headline (post-Phase-2, post-design-finalised). Calls Gemini 3.5 Flash with the chain's module list + reference images for the class. Emits manual-review badge if class/category mismatch detected.
What it addsCatches what text-only audits miss. The iter-7 cabinet-image-on-container-brief WAS caught by my visual read but missed by 4 text-only council members.
Tangible value: iter-7 image finding (cabinet shown for 40ft container brief) — would have been caught automatically by W2, surfacing a manual-review badge BEFORE Tristan looked at the PDF.

W6-full — Continuous learning

Plug-in pointTelemetry pipe (logs every chain action) + drift dashboard (weekly digest). User-signal capture: brief revisions, supplier overrides, cost manual edits. NO auto-mutation into production — diffs proposed to Tristan only.
What it addsThe "gets better every day" property — but human-gated, not autonomous. Detects when class quality drifts. Today's iter-8 work was essentially a manual version of W6-full.
Tangible value: if VF quality drops (e.g., new Generator model regressed humidity strategy), W6-full's weekly digest flags "VF gate-pass rate dropped from 87% → 71% — investigate". Without it, regressions accumulate silently.

Open questions for council

  1. Is W0 (object model) viable as a 2-week deliverable? Replacing 5+ scattered registries (class-priors, class-connections, class-suppliers, class-standards, class-floors) with one typed graph is a big surgical edit. Could be 4-6 weeks if there's significant Phase 1 generator rework.
  2. Should W1 tools be Python-subprocess or in-process TypeScript? Council previously said Python; the ts-codebase doesn't currently spawn Python (it spawns tsx). Subprocess overhead adds latency.
  3. For W3 specialists: route per-module, or per-finding? Per-module is simpler but a finding can span modules (e.g. LED-driver mismatch is Module 4 BoM + Module 5 electrical sizing).
  4. How big should the W6-lite harness be? 15 briefs is a starting point. Should it grow? Council previously said ≥20 per class for distillation — does the harness need that too?
  5. Should the council itself participate in W6-lite verification? Run council on every harness output, automatically — surfacing findings as additional regression signals?
