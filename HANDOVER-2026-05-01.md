## Critical Gotchas (WILL bite you if you don't know)

### 1. `autopilot_state` is JSONB, not flat columns

The table `cad_lab_projects` uses a **SINGLE** `autopilot_state` JSONB column. There are **NO** flat columns like `autopilot_stage`, `autopilot_status`, `autopilot_attempts`. Writing to those column names does nothing — the columns don't exist, and the SQL silently succeeds without error.

The cron reads from `autopilot_state->>'stage'`, `autopilot_state->>'status'`, etc. The field inside the JSONB is `stage` (**NOT** `current_stage`).

### 2. `started_at` must be non-null

The cron filters out projects where `autopilot_state->>'started_at'` is null. Any reset **MUST** set `started_at` to a non-null value or the project becomes completely invisible to the cron — it will never be dispatched.

### 3. Correct reset SQL (use this, not the flat-column version)

```sql
UPDATE cad_lab_projects
SET autopilot_state = jsonb_build_object(
  'stage', 'waiting_chase',
  'status', 'idle',
  'started_at', now()::text,
  'total_resets', 0,
  'current_stage_attempts', 0,
  'completed_stages', '[]'::jsonb
),
stage_scores = '{}'::jsonb,
ai_cost_estimates = NULL
WHERE id IN ('0ab0457a', '365eb5bf', '3acf3007', '330e1bec', '517ae649')
AND foundry_id = 'forge-guild';

DELETE FROM pipeline_runs
WHERE project_id IN ('0ab0457a', '365eb5bf', '3acf3007', '330e1bec', '517ae649');
```

### 4. Cron re-scores without re-running specialists

When score < 8/10, the cron dispatches `score_and_gate` which re-evaluates the **SAME** data in the database. It does **NOT** re-run the specialist to generate fresh output. To force a fresh specialist run, you must clear the relevant data column (e.g. `ai_cost_estimates = NULL` for Stage 6 finance). Without clearing, it will re-score the same data 15 times, get the same score, then mark `terminal_fail`.

### 5. OpenAI + Google direct API quotas exhausted

Do **NOT** use `callOpenAI` or `callGemini` anywhere in new code. Route everything through OpenRouter via `callOpenRouter` or `councilViaOpenRouter`. OpenRouter credits are available and working. The specialist code (not just judges/scoring) still has some direct `callGemini` calls — see "What needs doing next" below.

### 6. BESS infeasibility

The BESS sizing solver declares infeasible — it calculates needing 7,718 m² of panel area but the brief specifies a 21 m² shipping container. The Stage 6 code has an infeasibility gate that blocks cost estimation when `solver_failed = true`. This is an **upstream** Stage 1/Stage 2 problem — the brief needs to specify realistic capacity for a shipping container form factor (~30 m²). A shipping container is one of the most standardised form factors in the world — the engine should design within those constraints.

### 7. DeepSeek V4-Pro `reasoning_content`

DeepSeek V4-Pro is a reasoning model that puts output in the `reasoning_content` field, **not** `content`. Any code reading DeepSeek V4-Pro responses must check both fields:

```typescript
const text = msg.content || msg.reasoning_content || '';
```

The `callOpenRouter` function in `judge-panels.ts` already handles this (default `suppressReasoningFallback: false`), but verify this in any new code paths.

### 8. Deterministic stages must NOT be LLM-scored

Stage 3 (sizing) and Stage 4 (layout) are deterministic solvers. LLM scoring produces random scores on identical output → infinite retry-reset loops. These use hard-gate validators (convergence, unit consistency, constraint satisfaction). See `STAGE_VALIDATION_MODE` in `stage-scoring.ts`. 6/6 council consensus confirmed this on 2026-04-30.
