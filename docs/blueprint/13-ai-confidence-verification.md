## 1. Executive Summary

The AI Confidence & Verification system tracks the **provenance** of all content in Manufacturing Blueprints and enforces **human oversight** of AI-generated outputs. It integrates with CentaurOS's existing task workflow system rather than creating parallel structures.

### 1.1 Core Principles

1. **Provenance is Immutable**: Once content is created, its origin (`template_derived`, `user_entered`, `ai_suggested`) cannot be changed—only the verification status evolves.

2. **Confidence is Honest**: AI outputs include honest uncertainty estimates. Low-confidence outputs require stricter review gates.

3. **Tasks are the Review Mechanism**: All AI outputs that require approval flow through the existing `task_status` state machine. No parallel approval systems.

4. **Artifacts vs Tasks**: Blueprint artifacts (domain trees, expert packets, RFQ specs) are stored in `tasks.metadata` when actionable, or in domain-specific JSONB when informational.

5. **Human Approval is Logged**: Approval decisions are captured as `task_comments` with `is_system_log: true` for audit trail.

## 2. Provenance Model

### 2.1 Canonical Provenance Types

```typescript
type ProvenanceType = 'template_derived' | 'user_entered' | 'ai_suggested'
```

| Type | Definition | Verification Default | Example |
|------|------------|---------------------|---------|
| `template_derived` | Content copied from `blueprint_templates` or `knowledge_domains` | `approved` | Domain tree from "Consumer Electronics" template |
| `user_entered` | Content manually created by human user | `approved` | User adds custom domain "Battery Thermal Management" |
| `ai_suggested` | Content generated by AI/LLM | `pending_review` | AI proposes domain tree from product description |

### 2.2 Provenance Metadata Schema

Every piece of AI-influenced content carries provenance metadata:

```typescript
interface ProvenanceMetadata {
  // Core provenance
  provenance_type: ProvenanceType
  created_at: string // ISO8601
  created_by: string // profile_id (user or AI_Agent)
  
  // AI-specific fields (only for ai_suggested)
  ai_context?: {
    confidence: number // 0-100, required for ai_suggested
    confidence_factors: string[] // e.g., ["high_template_match", "limited_context"]
    rationale: string // Why AI made this suggestion
    assumptions: string[] // What AI assumed to be true
    model_metadata: {
      model_id: string // e.g., "gpt-4-turbo-2024-04-09"
      temperature: number // e.g., 0.3
      prompt_version: string // e.g., "expert_packet_v2.1"
      tokens_used: number
      generation_timestamp: string // ISO8601
    }
    source_context: {
      blueprint_id?: string
      domain_id?: string
      project_stage?: string
      product_description?: string
      referenced_decisions?: string[] // decision IDs used as context
    }
  }
  
  // Verification state
  verification: {
    status: VerificationStatus
    verified_by?: string // profile_id of reviewer
    verified_at?: string // ISO8601
    review_notes?: string // Reviewer's notes
    amendments?: Amendment[]
  }
}

type VerificationStatus = 'draft' | 'pending_review' | 'approved' | 'rejected'

interface Amendment {
  amended_at: string
  amended_by: string
  amendment_type: 'edit' | 'partial_accept' | 'enhance'
  original_content_hash: string // SHA256 of original for audit
  amendment_notes: string
}
```

### 2.3 Provenance by Content Type

| Content Type | Where Stored | Provenance Location | Notes |
|--------------|--------------|---------------------|-------|
| Domain tree (from AI) | `knowledge_domains` | `knowledge_domains.metadata.provenance` | AI-proposed domains |
| Domain coverage | `blueprint_domain_coverage` | `decisions` JSONB | Coverage assessments |
| Expert packet questions | `tasks` | `tasks.metadata.provenance` | Via artifact_type |
| RFQ specifications | `rfqs` | `rfqs.specifications.provenance` | In custom_fields |
| Decisions/assumptions | `blueprint_domain_coverage.decisions` | Inline in decision object | Per-decision provenance |
| Risk assessments | Computed | Not stored—ephemeral | Recomputed on demand |

### 2.4 Confidence Score Rubric

AI outputs must include a confidence score (0-100) calculated using these factors:

| Factor | Weight | Description |
|--------|--------|-------------|
| **Template Match** | 30% | How closely product matches a known template category |
| **Context Completeness** | 25% | Amount of product context provided |
| **Domain Specificity** | 20% | Whether domain has structured key_questions |
| **Stage Clarity** | 15% | Whether project_stage is appropriate for the ask |
| **Historical Success** | 10% | Model's track record for similar generations |

**Confidence Bands:**
- **80-100**: High confidence — AI has strong template match + full context
- **60-79**: Medium confidence — Partial template match or limited context
- **40-59**: Low confidence — Novel product or sparse context
- **0-39**: Very low confidence — Highly speculative, requires extensive review

## 3. Verification Workflow

### 3.1 State Machine

The verification workflow uses the **existing `task_status` enum** for AI outputs that require action. This avoids creating parallel approval structures.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        AI OUTPUT VERIFICATION STATE MACHINE                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│    ┌──────────┐                                                             │
│    │  draft   │  AI generates content (not yet submitted)                   │
│    └────┬─────┘                                                             │
│         │ AI completes generation                                           │
│         ▼                                                                    │
│    ┌──────────────────────────┐                                             │
│    │   pending_review         │  Task status: 'Amended_Pending_Approval'    │
│    │   (awaiting human)       │                                             │
│    └────┬─────────────────────┘                                             │
│         │                                                                    │
│         ├──────────────────────┬──────────────────────┐                     │
│         │ Human approves       │ Human requests edits │ Human rejects       │
│         ▼                      ▼                      ▼                     │
│    ┌──────────┐         ┌──────────────┐       ┌──────────┐                │
│    │ approved │         │   amended    │       │ rejected │                │
│    │          │         │   (Amended)  │       │          │                │
│    └──────────┘         └──────┬───────┘       └──────────┘                │
│                                │                                            │
│                                │ Re-submitted                               │
│                                ▼                                            │
│                         ┌──────────────────────────┐                        │
│                         │   pending_review         │                        │
│                         │   (Amended_Pending_      │                        │
│                         │    Approval)             │                        │
│                         └──────────────────────────┘                        │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 Mapping: Verification Status ↔ Task Status

| Verification Status | Task Status | Who Can Transition | Next Actions |
|--------------------|--------------|--------------------|--------------|
| `draft` | N/A (not yet a task) | AI_Agent | Complete generation → submit |
| `pending_review` | `Amended_Pending_Approval` | Human (Exec/Founder) | Approve, Reject, or Request Edits |
| `approved` | `Accepted` | Human (from pending_review) | Content usable; can create follow-up tasks |
| `rejected` | `Rejected` | Human (from pending_review) | Content discarded; logged for learning |
| `amended` | `Amended` | Human (from pending_review) | AI regenerates based on feedback |

### 3.3 Tasks vs Blueprint Artifacts

**Critical Distinction:**

| Category | Definition | Storage | Example |
|----------|------------|---------|---------|
| **Task** | Actionable item requiring execution | `tasks` table with `metadata` | "Generate Expert Packet for FCC Certification" |
| **Blueprint Artifact** | Informational content attached to domain | Domain-specific JSONB (`decisions`, `ai_generated_context`) | AI-suggested domain tree, risk assessment |

**Decision Tree: Task or Artifact?**

```
Is this AI output...
├── Actionable? (needs human to do something)
│   └── YES → Create as Task
│       └── Use tasks.metadata.artifact_type
│           └── 'expert_packet' | 'rfq_pack' | 'decision_proposal'
│
└── Informational? (enriches blueprint context)
    └── YES → Store as Artifact
        └── Use domain-specific JSONB
            └── blueprint_domain_coverage.decisions
            └── blueprints.ai_generated_context
            └── knowledge_domains.metadata
```

## 4. Rules: Auto-Creation vs Approval

### 4.1 Auto-Creation Rules (No Human Gate)

These actions can occur automatically without human approval:

| Action | Condition | Rationale |
|--------|-----------|-----------|
| **Create draft task** | Always | Drafts have no effect until submitted |
| **Populate template domains** | Template is system-verified | Templates are pre-approved |
| **Compute risk score** | Always | Ephemeral calculation, not stored |
| **Generate marketplace recommendations** | Gap exists + provider matches | Recommendations are suggestions only |
| **Create system log comments** | Always | Audit trail, not content |
| **Update coverage metrics** | Human changed coverage status | Metrics are computed, not generated |

### 4.2 Human Approval Required

These actions MUST have human approval:

| Action | Required Approval Level | Gating Mechanism |
|--------|------------------------|------------------|
| **AI-proposed domain tree** | Founder/Executive | Must explicitly "Confirm" proposed tree |
| **Expert packet questions** | Any team member | Task `Amended_Pending_Approval` → `Accepted` |
| **RFQ specifications** | Founder/Executive | RFQ status `draft` → `open` requires confirm |
| **Decision/assumption recording** | Any team member | Decision `status: 'proposed'` → `approved` |
| **Coverage status change from AI** | Any team member | AI can suggest, human must click |
| **OptionSet commitment** | Founder/Executive | Confirmation dialog required |

### 4.3 Marketplace CTA Gating Rules

Marketplace CTAs (calls-to-action) appear only when ALL conditions are met:

```typescript
interface MarketplaceCTAGate {
  // All must be true for CTA to appear
  conditions: {
    // 1. Domain has verified gap
    domain_status: 'gap' | 'partial'
    
    // 2. Confidence threshold met
    recommendation_confidence: number // >= 60 required
    
    // 3. Stage-appropriate
    stage_allows_marketplace: boolean // concept, prototype, evt = true; dvt+ = warn
    
    // 4. Risk assessment allows
    domain_risk_level: number // 0-5; only show if <= 4
    
    // 5. User hasn't dismissed
    recommendation_not_dismissed: boolean
    
    // 6. Provider tier verified
    provider_tier: 'verified_partner' | 'approved' // Must be one of these
  }
}
```

**CTA Appearance Logic:**

```typescript
function shouldShowMarketplaceCTA(
  domain: DomainCoverage,
  recommendation: MarketplaceRecommendation,
  stage: ProjectStage
): { show: boolean; variant: 'prominent' | 'subtle' | 'none'; warning?: string } {
  
  // Gate 1: Must be gap or partial
  if (!['gap', 'partial'].includes(domain.status)) {
    return { show: false, variant: 'none' }
  }
  
  // Gate 2: Confidence threshold
  if (recommendation.match_score < 60) {
    return { show: false, variant: 'none' }
  }
  
  // Gate 3: Stage appropriateness
  const highStages = ['dvt', 'production', 'launched']
  if (highStages.includes(stage)) {
    return { 
      show: true, 
      variant: 'subtle', 
      warning: 'Late-stage engagement may have limited impact' 
    }
  }
  
  // Gate 4: Risk level
  const riskScore = computeDomainRisk(domain)
  if (riskScore >= 5) {
    return { 
      show: true, 
      variant: 'subtle', 
      warning: 'High-risk domain—consider multiple providers' 
    }
  }
  
  // Gate 5: Not dismissed
  if (recommendation.is_dismissed) {
    return { show: false, variant: 'none' }
  }
  
  // Gate 6: Provider verified
  if (!['verified_partner', 'approved'].includes(recommendation.provider_tier)) {
    return { show: false, variant: 'none' }
  }
  
  // All gates passed
  return { show: true, variant: 'prominent' }
}
```

### 4.4 RFQ Generation Rules

RFQ generation from blueprints follows strict gating:

| Condition | RFQ Action | Rationale |
|-----------|------------|-----------|
| Domain status = `gap` | Can generate RFQ draft | Gap implies need for supplier |
| Domain status = `partial` | Can generate RFQ draft + warning | May need supplementary support |
| Domain status = `covered` | Cannot generate RFQ | No supplier need |
| AI confidence < 50 | RFQ draft + extra review banner | Low confidence = more scrutiny |
| Stage = `concept` | RFQ draft + "exploratory" label | Early stage = price discovery |
| Stage = `dvt` or later | RFQ draft + "production-ready specs" prompt | Late stage = serious engagement |
| Critical domain | RFQ draft + mandatory checklist | Critical = can't skip review |

**RFQ Generation Gating Function:**

```typescript
interface RFQGenerationGate {
  allowed: boolean
  requires_extra_review: boolean
  warnings: string[]
  suggested_rfq_type: 'commodity' | 'custom' | 'service'
  checklist_required: boolean
}

function canGenerateRFQ(
  domain: DomainCoverage,
  blueprint: Blueprint,
  aiConfidence?: number
): RFQGenerationGate {
  const result: RFQGenerationGate = {
    allowed: false,
    requires_extra_review: false,
    warnings: [],
    suggested_rfq_type: 'custom',
    checklist_required: false
  }
  
  // Block if covered
  if (domain.status === 'covered') {
    result.warnings.push('Domain already covered—RFQ not needed')
    return result
  }
  
  // Allow for gap or partial
  result.allowed = true
  
  // Extra review for low confidence
  if (aiConfidence !== undefined && aiConfidence < 50) {
    result.requires_extra_review = true
    result.warnings.push('Low AI confidence—review specifications carefully')
  }
  
  // Stage-specific behavior
  if (blueprint.project_stage === 'concept') {
    result.warnings.push('Early stage—consider this exploratory')
    result.suggested_rfq_type = 'service' // Consulting-style engagement
  }
  
  if (['dvt', 'production', 'launched'].includes(blueprint.project_stage)) {
    result.warnings.push('Late stage—ensure production-ready specifications')
    result.checklist_required = true
  }
  
  // Critical domain check
  if (domain.is_critical) {
    result.checklist_required = true
    result.warnings.push('Critical domain—mandatory review checklist')
  }
  
  return result
}
```

### 5.2 Review Queue

The review queue is driven by tasks with `status = 'Amended_Pending_Approval'` and `metadata.artifact_type` set.

**Review Queue Query:**

```typescript
async function getAIReviewQueue(foundryId: string): Promise<ReviewQueueItem[]> {
  const { data, error } = await supabase
    .from('tasks')
    .select(`
      id,
      title,
      description,
      metadata,
      amendment_notes,
      created_at,
      updated_at,
      assignees:task_assignees(
        profile:profiles(id, full_name, role)
      ),
      objective:objectives(
        id,
        name,
        blueprint_id
      )
    `)
    .eq('foundry_id', foundryId)
    .eq('status', 'Amended_Pending_Approval')
    .not('metadata->artifact_type', 'is', null)
    .order('updated_at', { ascending: false })
  
  return data?.map(task => ({
    task_id: task.id,
    title: task.title,
    artifact_type: task.metadata?.artifact_type,
    blueprint_id: task.metadata?.blueprint_id,
    domain_id: task.metadata?.domain_id,
    confidence: task.metadata?.provenance?.ai_context?.confidence,
    generated_content: task.amendment_notes,
    created_at: task.created_at,
    waiting_since: task.updated_at,
    assignee: task.assignees?.[0]?.profile
  })) || []
}
```

### 9.2 EC-002: Concurrent Approval Attempts

**Scenario:** Two users try to approve/reject the same AI output simultaneously.

**Expected Behavior:**
- First action wins (optimistic locking)
- Second user sees conflict toast: "This item was already reviewed by [Name]"
- Second action is rejected
- Audit log shows both attempts

**Handling:**
```typescript
async function approveAIOutput(taskId: string, reviewerId: string) {
  const task = await getTask(taskId)
  
  // Check not already reviewed
  if (task.metadata?.provenance?.verification?.status !== 'pending_review') {
    throw new ConflictError(`Already reviewed by ${task.metadata?.provenance?.verification?.verified_by}`)
  }
  
  // Optimistic lock check
  const { error } = await supabase
    .from('tasks')
    .update({ /* ... */ })
    .eq('id', taskId)
    .eq('updated_at', task.updated_at) // Optimistic lock
  
  if (error) {
    throw new ConflictError('Task was modified by another user')
  }
}
```

### 9.3 EC-003: AI Suggests Domain That Already Exists

**Scenario:** AI proposes domain tree that partially overlaps with existing domains.

**Expected Behavior:**
- Duplicate detection runs before showing proposal
- Matching domains highlighted: "Similar to existing domain: [Name]"
- User can choose to: skip, merge, or create as new
- Provenance tracks the decision

**Detection Logic:**
```typescript
function detectDuplicateDomains(proposed: ProposedDomain[], existing: KnowledgeDomain[]): DuplicateResult[] {
  return proposed.map(p => {
    const matches = existing.filter(e => 
      levenshteinSimilarity(p.name, e.name) > 0.8 ||
      cosineSimilarity(p.description, e.description) > 0.7
    )
    return {
      proposed: p,
      potentialDuplicates: matches,
      confidence: matches.length > 0 ? 'high' : 'none'
    }
  })
}
```

### 9.7 EC-007: AI Generates Empty or Invalid Content

**Scenario:** AI returns malformed JSON or empty content.

**Expected Behavior:**

- Invalid content rejected with specific error
- Task not created in invalid state
- System logs the failure for model monitoring

**Validation:**
```typescript
function validateExpertPacketContent(content: unknown): ValidationResult {
  if (!content || typeof content !== 'object') {
    return { valid: false, error: 'Content is empty or invalid type' }
  }
  
  const packet = content as Partial<ExpertPacketContent>
  
  if (!packet.questions || packet.questions.length === 0) {
    return { valid: false, error: 'No questions generated' }
  }
  
  for (const q of packet.questions) {
    if (!q.question || q.question.length < 10) {
      return { valid: false, error: 'Question too short or empty' }
    }
    if (!q.why_it_matters) {
      return { valid: false, error: 'Missing "why it matters" for question' }
    }
  }
  
  return { valid: true }
}
```

### 10.1 Ghost Worker Integration

```typescript
// Extended Ghost Worker for blueprint artifacts
export async function runBlueprintAIWorker(
  taskId: string,
  artifactType: ArtifactType,
  context: BlueprintContext
): Promise<void> {
  const task = await getTask(taskId)
  
  // Build prompt based on artifact type
  const prompt = buildArtifactPrompt(artifactType, context)
  
  // Generate content
  const response = await openai.chat.completions.create({
    model: 'gpt-4-turbo',
    temperature: 0.3,
    messages: prompt.messages
  })
  
  // Parse and validate response
  const content = parseAIResponse(response, artifactType)
  const validation = validateArtifactContent(content, artifactType)
  
  if (!validation.valid) {
    await handleGenerationFailure(taskId, validation.error)
    return
  }
  
  // Calculate confidence
  const confidence = calculateConfidence(context, artifactType)
  
  // Update task with provenance
  await updateTask(taskId, {
    status: 'Amended_Pending_Approval',
    amendment_notes: JSON.stringify(content),
    metadata: {
      ...task.metadata,
      provenance: buildProvenanceMetadata(
        'ai_suggested',
        confidence,
        response,
        context
      )
    }
  })
  
  // Add system log
  await addSystemComment(taskId, {
    action: 'ai_generation_completed',
    artifact_type: artifactType,
    confidence,
    model_id: 'gpt-4-turbo'
  })
}
```

### 10.2 Task Status Flow Integration

The verification workflow uses existing task statuses:

```typescript
// Map verification actions to task status changes
const VERIFICATION_TO_TASK_STATUS: Record<string, TaskStatus> = {
  'approve': 'Accepted',
  'reject': 'Rejected',
  'request_amendment': 'Amended'
}

export async function handleVerificationAction(
  taskId: string,
  action: VerificationAction,
  reviewerId: string,
  notes?: string
): Promise<void> {
  const newStatus = VERIFICATION_TO_TASK_STATUS[action]
  
  // Update task status
  await updateTask(taskId, { status: newStatus })
  
  // Update provenance metadata
  await updateTaskMetadata(taskId, {
    'provenance.verification.status': action === 'approve' ? 'approved' : action === 'reject' ? 'rejected' : 'pending_review',
    'provenance.verification.verified_by': reviewerId,
    'provenance.verification.verified_at': new Date().toISOString(),
    'provenance.verification.review_notes': notes
  })
  
  // Add system log
  await addSystemComment(taskId, {
    action: `verification_${action}`,
    reviewer_id: reviewerId,
    notes
  })
  
  // If amendment requested, trigger re-generation
  if (action === 'request_amendment') {
    await queueRegeneration(taskId, notes)
  }
}
```
